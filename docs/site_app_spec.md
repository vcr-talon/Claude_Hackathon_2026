# 現場残量アプリ 指示書（Claude Code用）

2026-11-04

## 概要と前提

打設当日に、現場担当者がタブレットで「残っているスパン」をタップし、柱・梁の打ち上がり高さを選ぶと、残りのコンクリート数量と生コン車の台数が出る仕組みです。PCアプリにすでにある「4. 打設終盤の残量」（スパンを選んで打ち上がり高さを指定）をそのまま現場に持ち出すもので、重い計算はPCでスパンごとの表にしておき、タブレットは表を引いて足すだけにします。タブレット側に3D表示も部材形状も不要で、データは数百KBで済みます。

使い方の流れ

1. PCアプリで施工階（必要なら工区と数える部材）を決め、「4. 打設終盤の残量」の「タブレット用に書き出す」でデータファイルを保存する（スパンを選んでおく必要はない。全スパンを書き出す）
2. データファイルをメールやクラウドストレージでタブレットに送る
3. タブレットでアプリのURLを開き、「データを開く」で読み込む
4. 打設中、打ち終わったスパンをタップして消していく。いま打っているスパンは柱・梁の打ち上がり高さ（スラブ下・梁せい中央・入力値）を選ぶ。画面上部に残りの合計と「あと○台」が出る

前提

- PCアプリは今の方式（ローカルWebアプリ）のまま。書き出しのAPIとボタンを足すだけで、既存のAPIと計算結果は変えない
- スパンの定義は、PCアプリの `buildCells()` と同じ（隣り合う通り芯で囲まれたマス。外側の帯もマス）。スパンは平面を隙間なく分割するので、スパンごとの数量を足すと全体の数量になる（スパンをまたぐ梁は境界で切ってそれぞれに入る）
- タブレットアプリは新しいフォルダ `site_app/` に、HTML・JS・CSSだけで作る。サーバーもPythonもThree.jsも使わない（平面図はSVG）
- iPad（Safari・Chrome）とAndroid（Chrome）の両方で動かす
- データはタブレットの中だけで扱い、どこにも送信しない。アプリ本体（配信するファイル）にBIMデータを含めない
- 数量の定義はPCアプリの「打設終盤の残量」と同じ。タブレットで同じスパン・同じ高さを選んだとき、PCの表示と 0.01 m³ 以内で一致すること

## PC側：タブレット用に書き出す機能

「4. 打設終盤の残量」で今サーバーがその場で計算しているものを、全スパン × 全ての打ち上がり高さについて先に計算し、表として書き出します。既存の「早見表をCSVで書き出す」の発展形です。

**1-a. 画面**

- 「4. 打設終盤の残量」の「早見表をCSVで書き出す」の横に「タブレット用に書き出す」ボタンを追加。スパンを選んでいなくても押せる（全スパンを書き出す）。ファイル名は `<高さ範囲>_<工区>_現場用_<月日>_<時分>.json`（例：`5SL～6SL_A・B工区_現場用_1105_1430.json`。iPadの一覧で省略されても見分けられるよう、高さ範囲と工区を先頭にする。IFC名はファイルの中の `source` にある。2026-11-05 変更）
- 書き出しが終わったら「タブレットに渡す」案内を出す：残量チェックの公開URLのQRコード（`frontend/site_app_qr.svg`。URLだけで数量のデータは入れない）、ファイル名、送り方と「最近使った項目」から選ぶ手順（2026-11-05 追加）
- 対象はいまの条件（高さ範囲・数える部材・数える材料・工区）。工区を分けているときは、スパンを工区の境界でさらに切って「X3～X4×Y2～Y3（A）」のように工区名を付ける。工区を分けていなければそのまま
- 計算中は進捗（「スパン 34 / 120」）をトーストに出す。完了時に「スパン n 件・合計 ○○ m³ を書き出しました」
- 未計算部材があれば、書き出し前に「未計算 n 件は含まれません」と注意を出す（書き出しは止めない）

**1-b. API**

- `POST /api/export_site` を追加。入力は「スパンの多角形の配列（名前付き）、z0、z1、categories、materials、step（既定 0.05）」。スパンの多角形は画面側の `cells` をそのまま送る（工区で切るのも画面側で `state.regions` との交差を取ってから送る。難しければサーバー側でshapelyの `intersection`）
- 出力は次の章のJSON。既存のAPIの入出力は変えない

**1-c. スパンごとの計算（高さ→体積の表）**

スパンごとに「柱・梁などスラブ以外」と「スラブ」に分けて計算します。PCアプリの `remainParts()` と同じ分け方です。

- スパンごとに `compute()` を呼び、スラブ以外の和集合（`Result.union`）とスラブの和集合を得る（2回の `compute()` でよい）。工区の登録済み部分の差し引き（`exclude`）は行わない（打設当日の対象はこの範囲全部のため）
- スラブ以外の和集合について、上端 z1 から `step` ずつ下げた高さ z1−k·step より上にある体積を求め、配列 `from_top`（k＝0が0、最後がそのスパンのスラブ以外の全量）にする。求め方は和集合を水平面で切る（manifold3d の `trim_by_plane`。なければ大きな直方体との `Intersect`）。スパンごとの小さな立体を切るだけなので、1回数ms。120スパン × 60刻みでも数十秒で終わる想定
- 最後の刻みは下端 z0 で止める（端数を残す）
- スラブは全厚の体積 `slab` を1つだけ（打つか打たないかの2状態）
- スパンごとに、打ち上がり高さの目安 `slab_bottom_mm`（そのスパンのスラブ下端）と `beam_mid_mm`（梁せい中央）を、`presetDepth()` と同じ考え方（上端付近の部材の中央値）で求めて入れる。該当部材がなければ null
- 検証：全スパンの `from_top` の最後の値 ＋ `slab` の合計が、同じ条件での「いまの条件の数量」（重複を除いた総数量）と 0.01 m³ 以内で一致すること。スパン内ではスラブと梁の重なりを別々に数えるので完全には一致しない。差は `overlap_note` としてファイルに記録し、大きければ（1%超）スラブの和集合からスラブ以外の和集合を差し引いてから `slab` を求める

**1-d. 平面図用の軽い形状**

- タブレットの平面図はSVGなので、部材の形状は送らない。代わりに、高さ範囲に入る部材ごとの平面の外接矩形 `[x0, y0, x1, y1]` と種別を `footprints` として入れる（数十KB）。柱・梁・壁の位置が分かれば現場での確認には十分
- 通り芯（`grids`）とスパンの多角形（`ring`）も入れる

## 書き出すファイルの形式

1ファイル＝打設当日の高さ範囲（つまり1フロア）です。単位はメートルと m³、値は丸めずに出します（表示だけタブレットで丸める）。

トップレベル

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `format` | 文字列 | 固定で `ifc-concrete-qto/site`。タブレットはこれ以外を開かない |
| `version` | 数値 | 1 |
| `exported_at` | 文字列 | 書き出し日時（ISO 8601） |
| `source` | 文字列 | IFCのファイル名（パスは含めない） |
| `title` | 文字列 | 画面に出す名前。例：「5SL～6SL」、工区があれば「5SL～6SL A工区」 |
| `conditions` | 文字列の配列 | 条件の説明（高さ範囲、数える部材、数える材料） |
| `z0` / `z1` | 数値 | 高さ範囲の下端と上端 |
| `step` | 数値 | 表の刻み（通常 0.05） |
| `total` | 数値 | この範囲の総数量（重複を除いた値。PCの「いまの条件の数量」と同じ） |
| `overlap_note` | 数値 | スパンごとの合計と `total` の差（参考） |
| `truck_m3` / `extra_pct` | 数値 | 生コン車の積載量と割増の初期値（PCの入力値を引き継ぐ） |
| `uncomputed` | 配列 | 未計算部材 `{name, category, reason}` |
| `storeys` | 配列 | `{name, elevation}`。高さを「6SL−800」のように表示するため |
| `grids` | 配列 | `{tag, start, end}`。平面図の通り芯 |
| `bounds` | [x0, y0, x1, y1] | モデルの平面の外形 |
| `footprints` | 配列 | `{category, box: [x0, y0, x1, y1]}`。平面図の下敷き |
| `cells` | 配列 | 下の「スパン」の配列 |

スパン（`cells` の中身）

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `id` | 文字列 | PCアプリの `cells[].id` と同じ（工区で切ったときは `#A` を付ける） |
| `label` | 文字列 | 「X3～X4×Y2～Y3」。工区があれば「（A）」を添える |
| `ring` | [[x, y], …] | スパンの多角形 |
| `from_top` | 数値の配列 | スラブ以外の部材のうち、上端から k·step 下までにある体積。先頭は0、最後が全量 |
| `slab` | 数値 | スラブの体積（全厚） |
| `slab_bottom_mm` / `beam_mid_mm` | 数値またはnull | 打ち上がり高さの目安（範囲の上端からの距離。部材はコン天付近で探す。画面ではコン天からの距離に直して使う） |
| `con_top` | 数値 | コン天の高さ（m）：高さ範囲の中で一番上のSL、なければ上端（D33）。古いデータにはなく、画面が階の高さから求める |
| `members` | 数値 | スパンに入る部材の件数（表示用） |

ファイルサイズの目安は 100～300KB です。メールやチャットでそのまま送れます。

## タブレットアプリ：画面と操作

画面は「上：残りの合計、中央：平面図（SVG）、下：打ち上がり高さと生コン車」の3段です。PCアプリの「4. 打設終盤の残量」と同じ言葉と並びにし、PCで覚えた操作がそのまま使えるようにします。手袋をした指でも押せるよう、ボタンは高さ 48px 以上、文字は 16px 以上。

**3-a. 起動とデータを開く**

- 初回は「データを開く」ボタンだけを大きく出す（`<input type="file" accept=".json,application/json">`）。下に「PCアプリの『タブレット用に書き出す』で作ったファイルを選んでください」と案内
- `format` が違う、または壊れているファイルは「このアプリ用のデータではありません」と表示
- 前回の作業が保存されていれば「前回の続きを開く（タイトル・最終更新時刻）」も並べる（5章の自動保存）
- 未計算部材があれば、開いた直後に「数量に含まれない部材が n 件あります」と一覧を出す

**3-b. 上段：残りの合計（常に表示）**

- タイトル、「予定 372.90 m³」、「打設済み 300.12 m³」、「残り 72.78 m³」。残りを一番大きく
- その下に「割増 3% 込み 74.96 m³　4.25 m³ × 17台 ＋ 最終車 2.71 m³（計 18 台）」。文面はPCアプリの `truckPlan()` と同じ
- 残りスパンの数（「残り 3 スパン」）も並べる

**3-c. 中央：平面図（SVG）**

- `grids` で通り芯と記号、`footprints` で柱・梁・壁の位置を薄く描き、その上にスパン（`ring`）を重ねる。Three.jsは使わない。平面図は縦横どちらでも画面に収まるよう `viewBox` で合わせ、2本指で拡大・移動できる
- スパンの色：未打設＝白、打設中＝オレンジ（PCアプリの「残りのスパン」と同じ色）、打設済み＝濃い灰色。スパンの中央に残り数量（例：12.4）を小さく出す
- タップで状態が巡る：未打設 → 打設中 → 打設済み → 未打設。長押しでそのスパンだけの打ち上がり高さを変えられる（下段にスパン名が出て、そのスパンだけの値になる）
- 打設の進み方に合わせ、「打設済みをまとめて」ボタンで打設済みモードにし、なぞったスパンを一度に打設済みにできる（優先）

**3-d. 下段：打ち上がり高さと生コン車**

- 「柱・梁の打上り：上端 − [ 0 ] mm」と、ボタン「スラブ下」「梁せい中央」「未打設（全量）」。PCアプリと同じ並び。ボタンの値は打設中のスパンの `slab_bottom_mm` / `beam_mid_mm` の中央値。数字キーボードを出す（`inputmode="numeric"`）
- この値は「打設中」のスパン全部にかかる。スパンごとに変えたときはそのスパンの値が優先
- 「生コン車 [ 4.25 ] m³／台　割増 [ 0 ] %」。初期値はファイルの `truck_m3` / `extra_pct`
- 「元に戻す」ボタンを常時表示。直前の操作を取り消す（履歴を持つので何回でも戻せる）

**3-e. 記録（優先）**

- 操作のたびに「時刻・スパン・状態・打ち上がり高さ・その時点の残り合計」を履歴に残す。「履歴」タブで新しい順に表示
- 「記録を共有」で履歴とスパンごとの最終状態をCSV（UTF-8 BOM付き）にして `navigator.share` で送る。使えない端末ではダウンロード

## タブレットアプリ：残り数量の計算

スパンごとの残りは状態で決まり、合計はその足し算です。打設中のスパンは、PCで作った表を直線で補間して求めます。タブレットの計算はこれだけです。

| スパンの状態 | 残り |
| --- | --- |
| 未打設 | `from_top` の最後の値 ＋ `slab` |
| 打設中（柱・梁を上端−d mm まで打設済み） | `interp(from_top, d)` ＋ `slab` |
| 打設済み | 0 |

```latex
\mathrm{interp}(d) = c_i + (c_{i+1} - c_i)\,\frac{d - i\cdot\mathrm{step}}{w_i}, \quad i = \left\lfloor d / \mathrm{step} \right\rfloor
```

c は `from_top`（m³）、d は上端からの距離（mm を m に換算）、w_i はその刻みの幅（最後の刻みだけ端数）です。d が表の範囲を超えたら最後の値（全量）を使います。

実装の要点

- 計算は純粋な関数 `remaining(cell, state, dMm)` と `interp(fromTop, step, z1 - z0, dMm)` にして画面から切り離し、下の例で単体テストする
- 表示は m³ 小数点2桁。内部は丸めない。打設済みの合計は「予定 − 残り」で出し、端数のずれを出さない
- 生コン車の台数はPCアプリの `truckPlan()` をそのまま移植する（同じ文面になる）

検算例（単体テストにする）

| 条件 | 期待する残り |
| --- | --- |
| 全スパンが未打設 | ファイルの `total` と `overlap_note` 以内で一致 |
| 全スパンが打設済み | 0.00 |
| 1スパンだけ打設中、d＝0 | そのスパンの `slab` だけ |
| 1スパンだけ打設中、d＝部材高さ以上 | そのスパンの未打設と同じ |
| 1スパンだけ打設中、d＝25（刻みの途中） | `from_top[0]` と `from_top[1]` の中点 ＋ `slab` |
| PCとの突合 | PCアプリで同じスパンを打設中にして同じ d を入れたときの表示と 0.01 m³ 以内 |

## iPad・Android両対応と配信

iPadではChromeもSafariと同じエンジン（WebKit）で動くので、「iPadのSafari」と「AndroidのChrome」の2つで動けば全部で動きます。両方で使える標準の機能だけを使います。

**5-a. 使うもの・使わないもの**

| 用途 | 使う | 使わない |
| --- | --- | --- |
| ファイルを開く | `<input type="file">` | File System Access API（`showOpenFilePicker`） |
| 記録を送る | `navigator.share`（ファイル付き）、予備にダウンロード | — |
| タッチ操作 | Pointer Events（SVG上のタップ・ピンチ） | Safari専用の `gesturestart` 等、ホバー前提の操作、右クリック・Shift・ホイール |
| 作業の保存 | `localStorage`（状態と履歴）、IndexedDB（最後に開いたデータファイル1件。`datastore.js`） | データファイル本体を `localStorage` に置くこと（容量制限に掛かるため） |
| オフライン | Service Worker でアプリ本体をキャッシュ | — |

**5-b. 画面と操作の決まり**

- 平面図に `touch-action: none` を付ける（ブラウザがページを拡大・スクロールしないように）。`<meta name="viewport">` で画面全体の拡大も止める
- タップの判定は「指を離したときの移動が 10px 未満」。スパンは大きいので当たり判定に困らないが、境界付近は近い方のスパンを拾う
- 縦向き・横向きの両方で崩れないこと。横向きでは下段の入力を右側のパネルにしてもよい
- 画面の文字は平易な日本語。内部用語（cell、from_top、member_id）を出さない

**5-c. 軽さ（安いAndroid端末でも動かす）**

- 平面図はSVGなのでWebGLは不要。要素数は通り芯＋部材の矩形＋スパンで数千以下に収まる
- スパンの色と数字だけを状態に応じて書き換え、平面図全体は作り直さない
- 拡大・移動は `viewBox` の書き換えで行う（Pointer Events で2本指を扱う）

**5-d. 自動保存**

- 入力のたびに、スパンごとの状態と履歴を `localStorage` に保存する。キーは「`source` + `title` + `exported_at`」。同じデータファイルを開き直したら自動で続きから再開する
- Safariは裏に回したタブを破棄することがあるので、この保存が打設中の作業を守る命綱になる
- 最後に開いたデータファイルは IndexedDB に1件だけ残し、最初の画面の「前回のデータで続ける」で開き直せるようにする（iPadではダウンロードしたファイルの場所が分かりにくいため。2026-11-05 変更）。端末の外には送らない。設定の「この端末に保存した作業をすべて消す」で一緒に消す
- 最初の画面に、ファイルが見つからないときの案内（「最近使った項目」、メール添付の「"ファイル"に保存」、ファイル名の形）を出す

**5-e. 配信（GitHub Pages）**

- `site_app/` をGitHub Pagesで公開する。HTTPSが自動で付き、Service Workerと `navigator.share` の条件を満たす
- 公開するのはアプリ本体だけ。データファイルやIFCを `site_app/` に置かない（`.gitignore` で `*.json` の誤コミットを防ぐ。`manifest.webmanifest` は除外にしない）
- `manifest.webmanifest`（アプリ名「残量チェック」など、アイコン192/512px、`display: standalone`）を置き、ホーム画面に追加できるようにする
- Service Workerはアプリ本体（HTML・JS・CSS・アイコン）だけをキャッシュ。更新時に古い版が残らないよう、キャッシュ名に版番号を付ける
- ファイルの中で使うパスはすべて相対パス（GitHub Pagesは `/<リポジトリ名>/` の下に置かれるため）

**5-f. 不具合を追うための仕組み**

- Windowsだけでは iPad の開発者ツールを開けないので、`window.onerror` と `unhandledrejection` を拾って、設定画面の「エラー記録」に表示する。内容をコピーできるようにする
- 設定画面にアプリの版番号を表示（キャッシュで古い版が動いていないか確かめるため）
