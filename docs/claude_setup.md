# Claude活用 指示書（Claude Code用）— 審査基準「Claudeの活用」対応

2026-11-04

## 狙いと現状

審査基準「Claudeの活用（25%）」は、①創造的な使い方・新しい可能性、②Claude Codeを開発の中心に据えたこと、③機能（Skills・サブエージェント・MCP・フック）の使い分け、の3項目です。このプロジェクトは②を実際にやっていますが、形に残っておらず、③はまだ使っていません。この指示書でその両方を埋め、①として「数量エンジンのMCPサーバー」を1つ足します。

貫く考え方は1つです。**積算の数字は間違えられないので、Claudeには数字を推測させず、検証済みの計算エンジンを安全に扱わせる**。要件D4・D5（推測で補わない）を、アプリだけでなく開発環境の作りにまで徹底する、という筋です。各機能にその役割を持たせると、「機能を使ってみた」ではなく「目的に応じて選んだ」と説明できます。

| 機能 | このプロジェクトでの役割 | 審査での見せ方 |
| --- | --- | --- |
| CLAUDE.md | 数量の定義・用語・許容値を前提として共有 | 要件が開発の全工程で効いている |
| フック | 計算エンジンを編集したら自動で数量検証。BIMデータの持ち出しを阻止 | AIがコードを触っても数字が狂わない仕組み |
| サブエージェント | 現場担当者の目と数量検証の目を、実装と切り離す | 作った本人が自分で採点しない |
| スキル | 検証・レビューの手順を毎回同じ品質で | 試行錯誤の踏み台が資産化されている |
| MCP | 数量エンジンをClaudeから日本語で操作 | 新しい使い方。LLMに積算を任せる不安への答え |
| モデルの使い分け | 設計の相談・実装・レビューで切り替え（すでに実施） | READMEに記述 |

前提

- 設定ファイルはすべてプロジェクト内（`CLAUDE.md`、`.claude/settings.json`、`.claude/agents/`、`.claude/skills/`、`.mcp.json`）に置き、GitHubに含める。審査員がリポジトリを見たときに分かるように
- 既存の計算エンジン・API・画面は変えない。MCPサーバーは既存の関数を包むだけ
- フックとスキルが呼ぶスクリプトは `.venv` のPythonで動かす（Windowsなので `.venv\Scripts\python.exe`）。シェルスクリプトではなくPythonスクリプトにするとWindowsでも確実

## 1. CLAUDE.md

プロジェクト直下に `CLAUDE.md` を置き、Claude Codeが毎回読む前提にします。長くしない（100行以内）。詳細は `docs/` を参照させる。

書く内容

1. **このアプリは何か**：3行。誰が、どんな場面で、何の数字を出すか
2. **数量の定義（最重要）**：D1（境界で切った幾何学的体積、重複は1回）、D4・D5（計算できないものは推定しない、モデルにないものは補わない）、D20（材料名で判定）、D26（内訳の配分順位）。「この定義を変える変更は、必ず先に確認を求める」と書く
3. **許容値**：要件の検証表（単純形状 1e-6、分割の整合 0.001 m³）と、実モデルの基準値（hackathon_model.ifc 全体 4377.07 m³、5SL～6SL 372.90 m³）。この数字が変わったらバグか定義の変更のどちらかなので、必ず報告する
4. **用語**：打設区分・工区・スパン・打設済み高さ・増し打ち・SL。画面の文言は現場向けの平易な日本語、内部用語を出さない
5. **構成と境界**：`backend/qto/`（計算。変えたら必ず検証）、`backend/server.py`（API。入出力は追加のみ）、`frontend/`（PC画面）、`site_app/`（タブレット。標準機能のみ、Three.jsなし）
6. **データの扱い**：IFC・`.qto_cache`・`.qto_uploads`・書き出したJSONはコミットしない。`hackathon_model.ifc` だけは公開可（D7）
7. **確認の仕方**：`pytest`、`scripts/check_model.py`、`node --test site_app/tests`。計算を触ったらフックが自動で走ること、その結果を無視しないこと
8. **進め方**：指示書（`docs/*.md`）の区切りごとに止まる。指示書とコードが食い違うときはコードを正として知らせる

注意：設計の経緯や全決定事項はCLAUDE.mdにコピーしない（`docs/requirements.md` への参照でよい）。毎回読まれるので、短いほど効く。

## 2. フック

`.claude/settings.json` に2つのフックを入れます。フックのスクリプトは `.claude/hooks/` にPythonで置き、標準入力のJSON（`tool_name`、`tool_input.file_path` など）を読んで動く。

**2-a. 計算エンジンを触ったら自動で数量を検証（PostToolUse）**

- 対象：`Edit|Write` で、編集したファイルが `backend/qto/` か `backend/server.py` のときだけ（スクリプト側でパスを見て、それ以外は何もせず終了）
- やること：`pytest -q backend/tests` を実行。続けて `scripts/quick_check.py`（新設）で `.qto_cache` のキャッシュから hackathon_model.ifc を読み、全体 4377.07 m³ と 5SL～6SL 372.90 m³ を 0.01 m³ 以内で確かめる。キャッシュがあれば合計で 30 秒以内。なければ「キャッシュなしのため実モデルの検証は省略」と出して止めない
- 結果：失敗したら終了コード 2 で標準エラーに「数量検証が失敗：全体 4377.07 → 4380.12。定義を変えたならその旨を、そうでなければ修正を」と書く。Claude Codeはこれを読んで次の手を打つ。成功時は何も出さない（静かに）
- `timeout` は 120 秒

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": ".venv\\Scripts\\python.exe .claude/hooks/verify_quantity.py", "timeout": 120 }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Edit|Write|Bash",
        "hooks": [
          { "type": "command", "command": ".venv\\Scripts\\python.exe .claude/hooks/guard_data.py" }
        ]
      }
    ]
  }
}
```

**2-b. BIMデータの持ち出しを止める（PreToolUse）**

- 対象：`Edit|Write` で書き先が `site_app/` 配下の `*.json`（`package.json` と `manifest.webmanifest` 以外）、または `.ifc` ファイルのとき。`Bash` でコマンドに `git add` と `.ifc` / `.qto_cache` / `.qto_uploads` / `_現場用_` が同時に含まれるとき
- 結果：終了コード 2 で「BIMから作ったデータは公開するフォルダに置かない（CLAUDE.md 6）」と書いて止める。hackathon_model.ifc だけは例外（D7）
- これはデモで「現場の図面データを誤って公開しない仕組み」として見せられる。社内導入の課題（U7）への答えの一つ

**2-c. やらないこと**

- 整形やlintのフックは入れない（残り時間ではノイズになる）
- フックが遅くて開発が止まるなら、実モデルの検証は `backend/qto/geometry.py` と `units.py` を触ったときだけに絞る

**2-d. 動作確認**

- `geometry.py` の `EPS_VOLUME` をわざと大きくして保存 → フックが失敗を知らせ、Claude Codeが自分で気づいて戻すことを確認（このやりとりを動画の素材にする）
- `site_app/テスト_現場用_x.json` を書かせようとする → 止まる

## 3. サブエージェント

`.claude/agents/` に2つ置きます（Markdown、先頭に `name` / `description` / `tools` のフロントマター）。どちらも「作った本人とは別の立場で見る」ためのもので、読み取り専用（`Read`、`Grep`、`Glob`、`Bash`）にしてコードを直させない。指摘を受けて直すのはメインのセッション。

**3-a. 現場担当者レビュアー `site-reviewer`**

- 立場：ゼネコンの工事主任。BIMソフトは使わない。打設の段取りと生コンの発注が仕事。コードは読まない。画面の文言と操作の流れだけを見る
- 入力：`frontend/index.html`、`site_app/index.html`、ヒント・トーストの文言（`app.js` から `toast(` と `hint` の文字列を grep）、あればスクリーンショット（4章のスキルが作る）
- 出力：「迷うところ」「意味が分からない言葉」「現場の段取りと合わない順序」を、改善案と一緒に最大5件。ほめ言葉は書かない。内部用語（offset、seed、cell、from_top）が画面に出ていたら必ず指摘
- 使いどころ：画面を変えた区切りごと。機能凍結前に全画面を一巡

**3-b. 数量検証役 `quantity-auditor`**

- 立場：積算担当。実装の説明を信用せず、数字だけを見る
- 入力：`docs/requirements.md` の検証表、`scripts/check_model.py` の出力、Archicadの数量（D29、`docs/archicad_*.csv` として置く）、`investigation/*.out.txt`
- やること：検証表①～④を順に実行し、差が許容値を超えた項目は「どの部材で、いくら、考えられる要因」を書く。壁341件の1%超の差（`check_model.out.txt`）の原因を、部材を数件選んで `investigation/` のスクリプトで追う。推測で埋めず「未確認」と書く
- 出力：`docs/verification.md` に検証結果表（日時・項目・期待値・実測・差・判定・要因）を追記。READMEの「信頼性」の章の根拠になる
- 使いどころ：11/7の検証日と、Archicadの数量が届いたとき

**3-c. 書き方の要点**

- `description` に「いつ使うか」を具体的に書く（例：「画面の文言や操作の流れを変えた後に使う」）。Claude Codeが自分で選んで呼ぶようになる
- 本文には「読むもの」「出力の形」「やってはいけないこと（コードを直す、推測で埋める）」を3つの見出しで
- 使った履歴が残るよう、レビュー結果は `docs/reviews/日付_名前.md` に保存させる。審査で「試行錯誤の跡」として見せられる

## 4. スキル

`.claude/skills/<名前>/SKILL.md` に3つ。「毎回同じ手順で確かめる」ことが目的なので、手順と合格条件を箇条書きで。スキルから呼ぶスクリプトは `scripts/` に置き、人が手でも実行できるようにする。

| スキル | いつ使うか | 手順 | 合格条件 |
| --- | --- | --- | --- |
| `verify-quantity` | 計算エンジンを変えたとき、機能凍結前、Archicadの数量が届いたとき | pytest → `scripts/check_model.py` → 工区A+B＝全体の確認 → タブレット書き出しの合計＝いまの条件の数量 → `docs/verification.md` に追記 | 要件の検証表①②の許容値内。基準値（4377.07 / 372.90）と 0.01 m³ 以内 |
| `ui-review` | 画面を変えた区切りごと | `scripts/screenshot.py`（Playwrightで localhost:8765 を開き、5SLの平面・境界線モード・打設リスト登録後・タブレット画面を4枚保存）→ `site-reviewer` に渡して指摘をもらう → 指摘を `docs/reviews/` に保存 | 内部用語が画面にない。指摘のうち「迷う」が0件になるまで繰り返すか、残す理由を書く |
| `site-export-check` | タブレット用の書き出しを変えたとき | `/api/export_site` を5SL～6SLで実行 → `from_top` の単調増加・先頭0 → 合計＝総数量 → `node --test site_app/tests` → ファイルサイズ | `overlap_note` が 0.01 m³ 未満、サイズ 300KB 以下、テスト全通過 |

書き方の要点

- `description` に「いつ使うか」を書く。Claude Codeが場面に応じて自分で選ぶ
- 手順はコマンドをそのまま書く（`.venv\Scripts\python.exe scripts/check_model.py`）。結果の読み方（どの行のどの数字を見るか）も書く
- 「失敗したらどうするか」を書く。共通して「数字を合わせるために許容値や基準値を変えない。変えるなら先に確認を求める」

## 5. MCPサーバー：数量エンジンをClaudeから使う

今のPython計算エンジンをMCPサーバーとして公開し、Claude Code（やClaudeデスクトップ）から日本語で数量を聞けるようにします。**Claudeは数字を推測せず、検証済みのエンジンを操作するだけ**。IFCそのものはClaudeに渡らず、返るのは数量と部材名だけです。これが「新しい使い方」の柱です。

**5-a. 構成**

- `backend/mcp_server.py` を新設。MCPのPython SDK（`mcp` パッケージの FastMCP）で stdio サーバーにする。起動時に `load_model()` でIFCを読む（キャッシュがあれば数秒）
- プロジェクト直下の `.mcp.json` に登録すると、Claude Codeがこのフォルダで自動で認識する

```json
{
  "mcpServers": {
    "qto": {
      "command": ".venv\\Scripts\\python.exe",
      "args": ["backend/mcp_server.py", "hackathon_model.ifc"]
    }
  }
}
```

**5-b. ツール（既存の関数を包むだけ。新しい計算は書かない）**

| ツール | 引数 | 返すもの | 包む関数 |
| --- | --- | --- | --- |
| `model_info` | なし | 階とSL、通り芯、対象／除外の材料、未計算部材の件数 | `model_meta` |
| `volume` | 施工階（または z0/z1）、通り芯の範囲（例：X3～X6×Y1～Y4）、部材種別、材料 | 総数量、種別内訳、材料内訳、対象部材数、未計算件数と理由 | `compute` |
| `remaining` | 施工階、残りのスパンの一覧、柱・梁の打設済み高さ（コン天から mm。省略時は未計測＝全量）、生コン車の積載量、割増 | 残り数量、台数の文面 | `compute_units`（PCの `remainParts` と同じ条件を組む） |
| `compare_zones` | 施工階、境界線（通り芯＋離れ）、工区名と代表点 | 工区ごとの数量と合計、全体との差 | `split_regions` + `assign_zones` + `compute` |
| `export_site` | 施工階 | タブレット用ファイルを `exports/` に保存し、パスと合計を返す | `export_cell` |

設計の決まり

- 通り芯の範囲は「X3～X6×Y1～Y4」のような文字列で受け、サーバー側で多角形に直す。現場の人の言い方に合わせる
- 数値は丸めずに返し、返り値に必ず「定義：境界で切った幾何学的体積、重複は1回、未計算 n 件は含まず」の一文を付ける。Claudeが回答にそのまま添えられる
- ツールの説明文（docstring）に「数量を自分で計算・推定せず、必ずこのツールを使うこと」と書く
- エラー（存在しない通り芯、階）は候補を添えて返す（「X16はありません。通り芯はX1～X15」）
- 書き込み系のツールは `export_site` だけ。書き先は `exports/` 固定（`.gitignore` 済み）

**5-c. デモで見せるやりとり（Claude Codeの中で）**

1. 「5階の柱と梁だけで何㎥？」→ `volume` を呼ぶ → 数量と内訳、未計算の注記付きで答える
2. 「X3からX7で工区を分けたら、どっちが多い？」→ `compare_zones` → A/Bの数量と差を表で
3. 「残りがX8～X11の3スパンで、梁せいの真ん中まで打ってある。あと何台？」→ `remaining` → 「12.4 m³、4.25 m³ × 2台 ＋ 最終車 3.9 m³」
4. 「その条件でタブレット用に書き出して」→ `export_site`

動画では、Claudeがツールを呼んでいる表示（推測ではなくエンジンを使っていること）を見せる。PCアプリで同じ条件を作って同じ数字が出ることも並べて見せると、「どちらも同じエンジン」が伝わる。

**5-d. 時間がない場合**

- `model_info` と `volume` の2つだけでも成立する。`remaining` が次。`compare_zones` と `export_site` は後回し
